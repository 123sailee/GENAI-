# WeekendYatri — Interview Prep & Technical Walkthrough

## 1. 60-Second Elevator Pitch

> "WeekendYatri is a production-ready Retrieval-Augmented Generation and LangGraph travel-planning API for Maharashtra weekend getaways—covering hubs like Nashik, Bhandardara, Ahilyanagar, and Chhatrapati Sambhajinagar. Generic LLMs frequently hallucinate regional bus fares, distances, and seasonal access, so I built a grounded pipeline backed by curated district government portals, state tourism pages, and Wikivoyage records in ChromaDB. Every answer returns verifiable source citations and explicitly abstains with `'I don't know'` when evidence is missing. Beyond Q&A, a LangGraph stateful agent routes cost queries through a human-in-the-loop approval gate before executing deterministic `own_car` vs. `msrtc_bus` fare, stay, and food calculators. Deployed on Render's 512 MB tier with lazy-loaded embeddings, LRU/TTL response caching, prompt-injection guards, and `/metrics` telemetry, it cuts repeat query latency from 727 ms down to 0.04 ms while maintaining 100% abstention on out-of-scope questions."

---

## 2. Hardest Engineering Problem (STAR Story)

- **Situation:** WeekendYatri ingests regional Maharashtra destination records from three heterogeneous sources—official district websites (`maharashtra.gov.in`), state tourism portals, and Wikivoyage—to answer both destination queries and month-specific trip recommendations.
- **Task:** Unify duplicate entries across sources that used inconsistent naming, historical renamings, and spelling variants (`Aurangabad` vs. `Chhatrapati Sambhajinagar`, `Ahmednagar` vs. `Ahilyanagar`, `Randha` vs. `Randhha`), while attaching deterministic seasonal rules so recommendations adapt dynamically to the travel month.
- **Action:**
  1. Built a canonical normalization and alias-mapping dictionary during ingestion to resolve renamed districts and phonetic spelling variants before chunking and indexing into ChromaDB.
  2. Deduplicated overlapping multi-source records by merging metadata (`source_url`, `district`, `category`) so each canonical destination retained authoritative citations without polluting top-$k$ retrieval slots with redundant chunks.
  3. Attached structured `best_season` rules (`Monsoon`, `Winter`, `Summer`, `Year-round`) mapped to calendar months so seasonal queries (e.g., monsoon waterfalls like Randha vs. winter treks) filter and rank context accurately.
- **Result:** Eliminated split/duplicate top-$k$ retrieval results across renamed districts, boosted retrieval recall from **0.7381 to 0.9167 (+24.2%)**, improved weighted evaluation score to **0.8313**, and achieved **100% unknown-answer abstention** on a 15-question benchmark.

## 3. Top 10 Likely Interview Questions & Answers

### Q1. Why did you use RAG instead of fine-tuning an LLM on Maharashtra tourism data?
**Answer:** Tourism advisories, road conditions, and MSRTC bus fares change periodically, and fine-tuning cannot guarantee verifiable source attribution or prevent parametric hallucinations. RAG lets us update the underlying corpus or CSV fare tables without retraining, attaches exact `source_url` citations to every claim, and enforces strict abstention (`"I don't know"`) whenever retrieved chunks lack evidence.

### Q2. How do you prevent the LLM from hallucinating prices, timings, or out-of-scope destinations?
**Answer:** Through three layers:
1. **Prompt & Schema Constraints:** `RAG_SYSTEM_PROMPT` instructs the model to rely *only* on retrieved JSON chunks, forbid inventing fares/timings, and return strict JSON.
2. **Programmatic Citation Validation:** In `app/rag.py`, every returned `(title, source_url)` pair is checked against the `valid_sources` set from the current retrieval pass; if no valid source matches, the response is overridden to `"I don't know"`.
3. **Deterministic Tooling:** Trip budgets are never generated by the LLM—they are computed by Python cost functions and verified MSRTC fare tables.

### Q3. How did you choose your chunk size and `top_k` retrieval parameters?
**Answer:** I ran an empirical benchmark across 15 test queries (14 answerable + 1 out-of-scope). Moving from **Config A** (`chunk=150, top_k=3`) to **Config B** (`chunk=300, top_k=5`) increased retrieval recall from **0.7381 to 0.9167 (+24.2%)**, improved answer keyword coverage from **0.6667 to 0.7976 (+19.6%)**, and reduced average response latency by **64.6%** (from 3.46 s to 1.23 s) while keeping 100% abstention accuracy.

### Q4. Why did you integrate LangGraph, and how does the Human-in-the-Loop (HITL) gate work?
**Answer:** WeekendYatri handles two distinct intents: informational Q&A and multi-parameter trip cost estimation. LangGraph models this as an explicit stateful workflow that classifies intent, gathers trip parameters (`origin`, `destination`, `travelers`, `days`, `mode`), and pauses at a human approval gate before executing cost tools (`own_car` fuel/toll estimator vs. `msrtc_bus` CSV fare lookup), ensuring users confirm assumptions before running budget calculations.

### Q5. How did you solve memory crashes when deploying to Render's 512 MB free tier?
**Answer:** Loading PyTorch, `sentence-transformers` (`all-MiniLM-L6-v2`), and `chromadb` eagerly pushed container RSS memory to **596 MB**, causing OOM restarts on Render's 512 MB limit. I refactored imports to lazy-load heavy vector dependencies (dropping cold-start RSS to **209 MB**) and added an environment-driven `USE_LIGHTWEIGHT_RETRIEVAL=true` mode using TF-IDF/keyword scoring for constrained containers while keeping full ChromaDB dense embeddings active locally and in CI.

### Q6. How does your caching layer work, and what impact did it have on latency and cost?
**Answer:** `app/llm.py` computes a SHA-256 cache key over `(MODEL_NAME, system_prompt, user_message)` backed by a bounded in-memory LRU + TTL cache. On the live Render deployment, an uncached Groq call (`openai/gpt-oss-20b`) takes **727.32 ms** and **1,479 tokens**, whereas a cached repeat request returns in **0.04 ms** (**99.99% latency reduction**) with **0 additional tokens**.

### Q7. How do you protect the API against prompt injection and abuse?
**Answer:** All incoming payloads pass through Pydantic length and range bounds (`question`/`message` 2–1,000 chars, `top_k` 1–20, `round_trip_km` <= 5,000) and a dedicated `app/security.py` sanitizer that detects instruction-override and system-prompt extraction patterns (e.g., *"Ignore all previous instructions"*), rejecting them with `HTTP 400` before any LLM call is made.

### Q8. How do you observe and debug the system in production?
**Answer:** FastAPI middleware attaches `X-Process-Time-Ms` headers to every response, and `GET /metrics` exposes live counters (`total_llm_calls`, `cache_hits`, `cache_misses`, `total_prompt_tokens`, `total_completion_tokens`, `total_tokens`, and `last_latency_ms`), allowing instant verification of cache hit ratios, token spend, and latency spikes.

### Q9. How is the codebase tested and verified before deployment?
**Answer:** GitHub Actions CI runs `ruff check .` for static linting and `pytest -v` (13 automated unit and integration tests) on every push. Tests use a deterministic fake LLM stub so CI validates endpoint schemas, cost calculators, citation filtering, input limits, prompt-injection blocking, and cache telemetry without external API flakiness.

### Q10. If you had two more weeks, what would you improve next?
**Answer:**
1. **Hybrid Dense + BM25 Retrieval with Reranking:** Combine ChromaDB embeddings with lexical BM25 and a lightweight cross-encoder reranker so exact proper nouns (like newly renamed districts or forts) and semantic queries both score optimally.
2. **Redis Shared Cache & Rate Limiting:** Move the in-memory LRU cache and per-IP rate limiting to Redis so telemetry and cached responses persist across container restarts and horizontal workers.
